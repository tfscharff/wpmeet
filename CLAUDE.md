# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Single-file WordPress plugin (`meet-a-librarian.php`) for Wheaton College's Madeleine Clark Wallace Library. It gives the library a "Meet With a Librarian" directory to replace LibCal Appointments. There is no build step, package manager, or linter config. The PHP file is the whole plugin. To release it, zip the file and upload it through wp-admin (**Plugins → Add New → Upload Plugin**). Targets WP ≥ 5.6 and PHP ≥ 7.2, so avoid newer PHP syntax such as arrow functions (7.4+), union types, `match`, `str_contains`, and trailing commas in function calls.

**Tests** (`tests/`, not shipped in the release zip) run offline against in-memory fakes of WordPress and Google Calendar (`tests/wp-stubs.php`). Run them before every release:

- `php -l meet-a-librarian.php`: syntax.
- `php tests/run.php`: which calendar event a request is matched to, when and how the librarian is emailed, and what the form handler and roster save accept. Every matching bug that has shipped has a case here; add one for any new scenario before changing `meetlib_gcal_pick()`.
- `php -S 127.0.0.1:8123 tests/ui.php`: local preview of the patron page (`/`) and the directory editor (`/editor`). Append `?autotest=1` to run the scripted walkthroughs (`tests/ui-autotest.js`, `tests/editor-autotest.js`); results land in `<pre id="results">`. Headless: `msedge --headless=new --virtual-time-budget=15000 --dump-dom "http://127.0.0.1:8123/?autotest=1"`. Also `/editor?autotest=1` and `/editor?autotest=1&loadfail=1`.

The fakes are not WordPress: file uploads, real email, WP-cron, and the real Google API are only exercised on a live site.

The plugin version is set only in the `Version:` plugin header and follows semantic versioning. Bump it in every commit that changes the plugin: PATCH for bug and accessibility fixes, MINOR for new backward-compatible features, MAJOR for breaking changes (for example, changes to the shortcode, the REST routes, or the stored option or post-meta shape).

**Every version bump gets a GitHub release**, cut right after the commit that bumps it. To publish one:
1. Tag the release commit as `vX.Y.Z` with an annotated tag and push the tag.
2. Build `wpmeet-X.Y.Z.zip` from that commit. Extract with Git Bash (`git show <sha>:meet-a-librarian.php > ...`); piping `git show` through PowerShell rewrites line endings and corrupts the file. The zip must contain a `meet-a-librarian/` folder holding the PHP file. Keep that folder name even though the zip is named `wpmeet-*`: it's what lets an existing install upgrade in place.
3. Save the zip to `~/Downloads` (`C:\Users\thoma\Downloads\wpmeet-X.Y.Z.zip`).
4. Run `gh release create vX.Y.Z <zip> --latest`.

Breaking changes and upgrade steps go at the top of the release notes; otherwise state that no setup needs redoing. Existing releases: `v1.2.1` (last 1.x; its zip keeps the 1.x plugin folder so an existing install upgrades in place), `v2.0.0`, and `v2.1.0` (the first release named `wpmeet-*.zip`).

## Architecture

The front-end and admin UIs are vanilla ES5 JavaScript and inline CSS. They sit in PHP **nowdoc** heredocs (`<<<'HTML'`), so PHP does not interpolate `$` inside them. PHP passes config to the JS through `window.*` globals that it prints just before each script:

- Admin editor: `window.MEETLIB`, set by `meetlib_admin_page()`, rendered by `meetlib_editor_markup()`.
- Shortcode `[meet_a_librarian]`: `window.MEETLIB_URL` and `window.MEETLIB_FORM`, set by `meetlib_shortcode()`, rendered by `meetlib_widget_markup()` and `meetlib_widget_script()`.

**Storage:** the plugin creates no custom tables. Option and CPT keys are referenced through the `MEETLIB_*` constants at the top of the file, not string literals.
- The librarian roster is one array in the `meetlib_librarians` option. Each row has exactly 8 fields: `name, pronouns, title, liaison, email, photo, profile, booking`. `meetlib_get()` returns `meetlib_default()` when the option is empty. Adding a field means updating `meetlib_sanitize()`, `meetlib_default()`, the editor's `FIELDS` and "add" row in JS, and the widget JS.
- The last 5 rosters replaced by a save are kept in `meetlib_librarians_backup` (`meetlib_backup_roster()`), restorable from the editor page ("Earlier versions", `admin_post_meetlib_restore`).
- The booking page URL is stored in the `meetlib_page_url` option.
- Patron appointment requests are stored as the private CPT `meetlib_request`, with answers in `_meetlib_*` post meta. Code is the only thing that creates these records (`create_posts => do_not_allow`). Staff view them read-only under the admin menu. They are kept forever (the user's decision).
- **Attachments are never kept.** An upload is held in `uploads/meetlib-private/<random>/` (`meetlib_hold_upload()`, path in `_meetlib_file`) only until `meetlib_notify()` has emailed it to the librarian as a real attachment, then deleted; `_meetlib_file_name` remains for display. Records from before 2.5 have a public `_meetlib_attach_url` instead; the Calendar Integration page offers a button to delete those files.
- Everything uses the `meetlib` / `MEETLIB` / `meet-a-librarian` prefix. Version 1.x stored data under an older prefix. `meetlib_migrate()` runs once on `init` to move that data and is the only code that refers to the old keys. It is guarded by the `meetlib_db_version` option (now 3; step 3 only raises the `meetlib_work` flag). If a later release changes the storage shape again, bump `MEETLIB_DB_VERSION` and add a new migration step.

**REST API** (`meet-a-librarian/v1`):
- `GET /librarians`: public. Both UIs load the roster from here (`meetlib_public_roster()`, which adds a computed `embed` scheduler URL per row; the editor strips it before saving).
- `POST /librarians` (`meetlib_save_roster`): requires `edit_pages`. Takes `{librarians, pageUrl}`, then runs the data through `meetlib_sanitize()`, a whitelist of the 8 roster fields. Rows without a name are dropped. **An empty result is refused**, and the editor refuses to save when its list failed to load: either would replace every booking link with the blank defaults.
- `POST /request` (`meetlib_handle_request`): public, for patron form submissions. No nonce (see below). Guards: honeypot (`meetlib_hp`; `website` from cached pre-2.5 pages is still honoured), email-domain whitelist, field validation, a 10-minute duplicate check, and rate limits per IP and per email. The flow is: resolve the librarian → validate → dedupe → rate-limit → hold the optional attachment → save a CPT record → decide the status (`meetlib_initial_status`) → either queue the first calendar check (`pending`) or email the librarian now → return `{ok, calendar, embedUrl, booking}` (`embedUrl`/`booking` are kept only for pages still serving the 2.0 script from a cache). **The handler never contacts Google**: the patron cannot have booked yet, and the form must not depend on Google being up.

**No nonce on the public form.** Before 2.5 the script sent a `wp_rest` nonce as `_wpnonce`. WordPress core rejects a stale one ("Cookie check failed") before the handler runs, so a booking page served from a page cache for over a day could not submit at all. The new script sends none; `meetlib_rest_stale_nonce()` (on `rest_authentication_errors`) downgrades a stale nonce from old cached pages to "anonymous" for this one route. Don't reintroduce a nonce or any token baked into the page HTML.

**Patron flow (2.3+):** one screen, two panels (side by side ≥960px, stacked below). Left: the short intake form. Right: the Google Calendar appointment schedule embedded through `?gv=true` (see `meetlib_embed_url`) with the `meetlib_urgent_email()` note under it. The scheduler sits behind a translucent `.meetlib-f__lock` overlay (iframe `tabindex=-1 aria-hidden`) until the form is sent, so patrons can see which dates have openings but cannot book without answering. `showDone()` removes the lock, reveals an "open in a new tab" fallback link, tells the patron which email to book with, and moves focus to the calendar heading. The sent state is remembered in `sessionStorage` for 30 minutes so a reload doesn't ask for the form again; "Send a different request" clears it. Links that are not Google appointment links fall back to a plain external link, locked the same way. The form does not ask for a name (Google's booking form collects it); it keeps email because that's how the Calendar integration matches the booking. **Form-first is the only enforceable order**: booking happens inside Google's cross-origin iframe, which the plugin can neither observe nor gate after the fact. History: 2.0 was form → calendar on separate screens; 2.1 flipped to calendar → "I've booked" gate → form (too clunky); 2.2 showed both unlocked (patrons could book and skip the form). Don't repeat those.

**Optional Google Calendar integration** (`meetlib_gcal_*`, admin page "Calendar Integration", `manage_options`): a service-account JSON key stored in the `meetlib_gcal_key` option (autoload off). No Workspace domain-wide delegation; each librarian shares their own calendar with the service account ("Make changes to events"), and the calendar ID is the roster `email`. The OAuth token comes from a hand-rolled RS256 JWT (`openssl_sign`, no Composer deps) and is cached in a transient. With no key saved, everything is a no-op (`off`).

- **Statuses** (`_meetlib_gcal`): `pending` (watching; email held), `added`, `not_found`, `no_access` (key rejected or calendar not shared/not writable: permanent until someone fixes it), `error` (network/outage: temporary), `no_calendar`, `self` (patron email equals the calendar ID: a librarian testing; emailed at once, never searched), `off`.
- **Checks:** `meetlib_gcal_retry()` runs at the offsets in `meetlib_gcal_retry_delays()` (3m, 10m, 30m, 2h, 6h, 24h after submission), counted in `_meetlib_gcal_tries`, next time in `_meetlib_gcal_next`, one worker at a time via `meetlib_lock()`. `not_found`/`error` keep waiting until the delays run out; `added` and `no_access` finish immediately. Finishing stores `_meetlib_when` (appointment start in the calendar's time zone via `meetlib_gcal_when()`, never the site's, which may be UTC), `_meetlib_event_link`, `_meetlib_hints`, then calls `meetlib_notify()`.
- **Matching** is `meetlib_gcal_pick()`, pure and covered by `tests/run.php`. `meetlib_gcal_list_since()` lists every event changed since the submission (no `q` text search, whose index lags; no upcoming-only filter). A booking must be created at or after the submission (converted to Google's clock using the `Date` response header, `$GLOBALS['meetlib_gcal_skew']`), list the patron's email as a guest other than `self`/`organizer`, and not be cancelled, recurring, or already tagged with `MEETLIB_GCAL_MARKER`. The **oldest** such event wins, so two forms sent back to back each take their own booking. The description is PATCHed (HTML, `sendUpdates=none`, `If-Match` etag). **Never add fuzzy matching**: a wrong match writes one patron's answers into an event whose guests can read them; a missed match only produces a "no booking found" email. A patron who books under another address ends as `not_found`; bookings made within 45 minutes under a different address are listed for the librarian as hints.
- **Problems:** a calendar that returns `no_access` is flagged in the `meetlib_gcal_problems` option. Flagged calendars are not watched for 6 hours (requests are emailed immediately), then retried, so they recover by themselves once re-shared.
- **Not depending on WP-cron:** each check is a WP-cron single event, but `meetlib_sweep()` also runs overdue checks and email retries at the end of ordinary page loads (`shutdown`, throttled to once per 2 minutes, only while the `meetlib_work` option is set) and from the "Run waiting checks now" button. `meetlib_health()` feeds admin notices on the plugin's screens (unusable calendars, overdue checks, failed emails).

**Librarian email** (`meetlib_notify( $post_id )`): built entirely from the stored record so it can be retried; sent once (`_meetlib_notified`). Wording by status: `added` → "Appointment booked: <when>", `not_found` → "no booking found" (plus hints and a note if the same patron has another matched request), `no_access`/`error` → calendar could not be checked, otherwise the plain request. With no librarian email on file it goes to `meetlib_urgent_email()`. A failed `wp_mail` is retried by the sweep (`_meetlib_mail_fails`, `_meetlib_mail_next`; 5 attempts, the last 3 without the attachment).

## Invariants to preserve

- **Form fields are defined once.** `meetlib_form_fields()`, `meetlib_email_domains()`, `meetlib_upload_mimes()` (from which `meetlib_upload_exts()` is derived), `meetlib_max_upload_bytes()`/`meetlib_max_upload_label()`, `meetlib_max_chars()`, and `meetlib_urgent_email()` are serialized into `MEETLIB_FORM` and drive client-side rendering and validation. The server repeats the same validation from the same functions (meeting options via `meetlib_field('meeting')`). The request handler's `$data` array and meta list, `meetlib_gcal_retry()`, the admin request view, `meetlib_notify()`, and `meetlib_gcal_details_html()` each list the text fields by hand, so a new field must be added to all of them. Records from before 2.2 also carry `_meetlib_first`/`_meetlib_last`; the admin view shows those only when present.
- **Slugs must match between PHP and JS.** `meetlib_slug()` in PHP and `slug()` in both JS blocks must produce the same slug (ASCII lowercase, non-alphanumeric runs become `-`, and leading/trailing `-` are trimmed). The deep link `?librarian=<slug>` automatically opens that librarian's booking step. The admin page generates copyable per-librarian widget HTML for LibApps/LibGuides profiles, and that HTML uses these links, so **renaming a librarian breaks their already-pasted widget**. `esc()` is likewise duplicated in both JS blocks, and the editor's `bookingNote()` mirrors `meetlib_embed_url()`.
- **Requests are routed by roster index plus slug.** The front end sends `librarian=<index>` and `librarianSlug`. If the slug doesn't match the row at that index (the roster was edited while the page was open), the server looks the librarian up by slug instead. Requests without a slug (2.0 cached pages) use the index alone.
- **Never make librarians redo setup.** Booking links, roster shape, the shortcode, REST routes, the widget deep-link format, the saved service-account key, and the calendar shares are what librarians and LibGuides pages depend on. New behavior must be additive or optional, and old cached copies of the page script must keep working against a newer server.
- **A request is never silently lost.** Every accepted submission is stored first; every stored request ends in an email to someone (the librarian, or the shared inbox), or in a visible warning on the admin screens. Keep that true when adding statuses or failure paths.
- **The `meetlib_request` CPT is added to the menu by hand** in `admin_menu`, after the editor, so the editor stays the default submenu (`show_in_menu => false`).
- Escaping: JS builds its HTML strings with the local `esc()` helper. PHP output uses `esc_html` or `esc_url`.
